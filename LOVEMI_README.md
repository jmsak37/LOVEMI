# LOVEMI

LOVEMI is a web-based social and dating platform built with HTML, CSS, JavaScript, PHP and MariaDB/MySQL. The project provides public discovery pages, authenticated member features, profiles, connections, real-time-style messaging endpoints, Premium access, payments, notifications, support tickets, administrator management and security controls.

> **Project path:** `C:\xampp\htdocs\LOVEMI`
>
> **Primary database:** `lovemi`
>
> **Database dump:** `database/lovemi.sql`

---

## 1. Project status and source of truth

This README describes the project using the current LOVEMI project tree supplied with the project and the current `lovemi.sql` database dump.

The current project tree contains public pages, administrator pages, PHP APIs, authentication libraries, payment integrations, email services, notification audio, uploads, cron jobs and backups. The tree also includes `Support-Ticket-Feedback.html`, the support API family, and the administrator Help Center API family.

The current database dump was generated by phpMyAdmin on **September 8, 2026**, using **MariaDB 10.4.32** and **PHP 8.0.30**. The dump targets the database named `lovemi` and uses `utf8mb4`.

## 4. Requirements

A local installation should provide:

1. Apache web server through XAMPP.
2. PHP compatible with the project code. The current database export identifies PHP 8.0.30.
3. MariaDB/MySQL compatible with the current SQL dump. The current export identifies MariaDB 10.4.32.
4. PHP extensions required by the installed libraries and database layer.
5. A browser with JavaScript enabled.
6. SMTP configuration for outbound LOVEMI email.
7. Payment-provider credentials before production payment flows are enabled.
8. HTTPS in production, especially for authentication, sessions, support links and payment callbacks.

## 5. Local installation with XAMPP

### Step 1 — Place the project

Copy the project to:

```text
C:\xampp\htdocs\LOVEMI
```

The public pages should then be reachable from:

```text
http://localhost/LOVEMI/
```

### Step 2 — Start XAMPP

Start:

- Apache
- MySQL

Make sure there is no port conflict with another Apache/MySQL installation.

### Step 3 — Create the database

Open phpMyAdmin:

```text
http://localhost/phpmyadmin/
```

Create a database named:

```text
lovemi
```

Recommended charset:

```text
utf8mb4
```

Recommended collation:

```text
utf8mb4_unicode_ci
```

### Step 4 — Import the SQL dump

Import:

```text
database/lovemi.sql
```

The dump already contains the schema, indexes, constraints, triggers, views and database data represented in the export.

### Step 5 — Configure database connection

Edit:

```text
config/database.php
```

Set the correct local database host, database name, username and password.

Typical local XAMPP values may be:

```text
Host: 127.0.0.1
Database: lovemi
User: root
Password: your configured MySQL password
```

Do not copy those values into production unless they actually match the production environment.

### Step 6 — Configure application settings

Review:

### Step 7 — Configure email

Review the central email service:


## 6. Production deployment

Before production deployment:

1. Use HTTPS.
2. Set a real public application URL.
3. Configure secure cookies.
4. Move secrets out of public source files.
5. Configure the production database separately from development.
6. Configure SMTP with a dedicated application credential.
7. Configure real payment-provider credentials and callback URLs.
8. Review Apache/PHP error exposure.
9. Protect backup files from public download.
10. Review `uploads/`, `storage/`, `.env`-style files if introduced later, and configuration directories for public access.

For email links, the application supports an `LOVEMI_APP_URL` environment value in its support URL helpers. A production deployment should use a real public URL instead of a localhost URL, otherwise recipients outside the server cannot open secure support links.

Example:

```text
LOVEMI_APP_URL=https://your-public-domain.example/LOVEMI
```

Only set the value in the environment/configuration actually used by the production PHP process.

## 11. Support verification

Account-owned support conversations can require:

1. A valid secure support token.
2. A logged-in account matching the ticket.
3. Email verification.
4. Google Authenticator verification.

The support verification code is stored as a hash. The verification endpoint should never expose the raw stored code or application secrets in a client-side page.

The project support workflow uses a short verification-code lifetime. The current support email verification implementation has been corrected to use a **2-minute (120-second)** code lifetime rather than 10 minutes.

Relevant files:



The design is intended to prevent ordinary public profile URLs from directly exposing raw numeric user IDs.

A secure profile code should be treated as an access identifier and validated server-side. Never trust a decoded client-side value without database validation and authorization checks.

- Connections reference users.
- Conversations reference users and may reference a connection.
- Messages reference conversations, senders and receivers.
- Notifications reference users, senders, notification types and audio.
- Payments reference users, currencies and services.
- Payment receipts reference payments.
- Photos reference users and optional approvers.
- Posts reference users and optional approvers.
- Post comments reference posts, users and parent comments.
- Post photos reference posts and photos.
- Profiles reference users.
- Reports may reference messages, posts and reported users.
- Countries reference currencies.

These relationships are represented by foreign-key constraints in the current dump.

## 28. Email architecture

The centralized LOVEMI email layer is under:

```text
services/email/
```

The normal application approach should be:

```php
require_once __DIR__ . '/services/email/email-service.php';

sendLovemiEmail(
    $recipientEmail,
    $recipientName,
    $subject,
    $htmlBody,
    $plainBody
);
```

Application features such as support, verification and payment notifications should reuse the centralized service rather than embedding SMTP credentials in each page/API.

### Email troubleshooting

If an email is not delivered:

1. Check PHP error logs.
2. Check the central email service.
3. Check SMTP host/port/security settings.
4. Check SMTP authentication.
5. Check the sender identity.
6. Check spam/junk folders.
7. Test with a known-good recipient.
8. Confirm the PHP process can make the required outbound SMTP connection.
9. Check whether the mail function/service returns `false`.

The API should distinguish between a database-successful operation and an email-delivery failure.

## 31. Security guidelines

### Sessions

- Use HTTPS in production.
- Use secure, HttpOnly cookies.
- Use SameSite cookie protection.
- Validate session expiration server-side.
- Revoke sessions on logout or administrator-required security events.

### Passwords

Passwords must be stored as secure password hashes, never plain text.

Use PHP functions such as:

```php
password_hash($password, PASSWORD_DEFAULT);
password_verify($password, $hash);
```

### SQL injection protection

Use prepared statements:

```php
$stmt = $pdo->prepare(
    'SELECT id FROM users WHERE email = :email LIMIT 1'
);
$stmt->execute([':email' => $email]);
```

### Output escaping

Escape user-generated content before placing it into HTML.

### Authorization

Never assume that a URL parameter, profile code, ticket ID or user ID belongs to the current user. Validate ownership or permission server-side.

### Support tokens

Secure support tokens should be stored as hashes in the database. Raw tokens should only be delivered through secure links or controlled API responses.

### Secrets

Never commit:

- SMTP passwords
- Payment API secrets
- OAuth secrets
- Encryption keys
- Database production passwords
- Private signing keys

## 33. Support troubleshooting

### Problem: Support link says invalid

Check:

```text
support_ticket_access
```

Confirm the token being supplied by the URL matches the stored hash generated by the application.

### Problem: Account verification code is not received

Check:

```text
api/support/feedback/send-email-code.php
services/email/email-service.php
services/email/mail.local.php
```

Also check the PHP error log and SMTP delivery status.

### Problem: Code expires too quickly or too slowly

The server-side expiration should be:

```sql
DATE_ADD(CURRENT_TIMESTAMP, INTERVAL 2 MINUTE)
```

The browser timer should use the `expires_in` value returned by the API.

### Problem: Direct Email / Message creates a ticket but does not send email

Check:

```text
admin-api/help-center/send-message.php
services/email/email-service.php
```

The operation should report mail delivery failure separately from ticket creation failure.

### Problem: Reply link points to localhost

Set the production application URL through the environment/configuration used by the PHP application, for example:

```text
LOVEMI_APP_URL=https://your-domain.example/LOVEMI
```

## 36. API conventions

Most LOVEMI APIs return JSON.

Typical successful structure:

```json
{
  "success": true,
  "message": "Operation completed."
}
```

Typical error structure:

```json
{
  "success": false,
  "message": "An error occurred.",
  "code": "SOME_ERROR_CODE"
}
```

Clients should:

1. Check HTTP status.
2. Parse JSON safely.
3. Check `success`.
4. Handle `code` values.
5. Display user-friendly messages.
6. Never display raw PHP errors to users.

## 41. Support data model

A support conversation is represented by three principal objects:

### `support_tickets`

Stores the ticket identity and high-level state such as user, name, email, category, subject, initial message and status.

### `support_ticket_access`

Stores secure access information including the ticket identifier, access type, token hash and verification-code state. The current SQL dump also includes email-code locking fields and 2FA attempt/lock fields.

### `support_ticket_messages`

Stores the threaded conversation messages with sender type, sender information, body and creation time.

This separation allows the support system to keep the ticket record, secure access record and message history independent while still linking them through the ticket ID.

## 43. Error handling philosophy

LOVEMI should fail safely.

Bad examples:

```text
Raw SQL errors in browser
SMTP password in JSON
PHP warnings before JSON output
Trusting user IDs from the browser
Granting support access after only a UI check
```

Better examples:

```json
{
  "success": false,
  "message": "The support verification code has expired.",
  "code": "CODE_EXPIRED"
}
```

Server logs should contain technical details while user-facing responses stay safe and understandable.

## 50. Notes for future developers

LOVEMI is a database-driven application. When fixing a bug, prefer tracing the complete path:

```text
HTML page
   ↓
JavaScript request
   ↓
PHP API
   ↓
Authorization/session check
   ↓
Database query/update
   ↓
Optional service (email/payment/notification)
   ↓
JSON response
   ↓
UI update
```

Do not solve a server-state problem only in JavaScript. Do not assume a successful HTTP request means that an email, payment or database transaction succeeded. Check the actual server result and return explicit status information.

For support tickets especially, always maintain consistency between:

```text
support_tickets
support_ticket_access
support_ticket_messages
```

For account verification, always keep browser countdowns and server-side expiration logic consistent. The server remains authoritative.
